# Redis DevRel CFP

Draft CFP material grounded in this repository's actual implementation. Keep claims concrete, technically accurate, and aligned with Redis DevRel expectations.

## Workflow

1. Read [references/project-context.md](references/project-context.md) before drafting.
2. Pull only substantiated details from the repo and project context. Do not invent benchmarks, production usage, or customer outcomes.
3. Frame the talk around a clear developer problem, the Redis-specific approach, and a practical demo arc.
4. Prefer concise, audience-friendly language over research-paper wording.
5. When the user asks for a CFP package, include:
   - 3 title options
   - 1 abstract
   - 3 audience takeaways
   - a short demo flow
6. When the user asks for a shorter artifact such as a single abstract or session pitch, still keep the Redis angle explicit.

## Messaging Priorities

- Lead with the developer problem: building voice or conversational apps that remember prior context.
- Explain the Redis role clearly: long-term memory, working memory continuity, semantic retrieval, and intent-aware routing.
- Highlight the end-to-end stack only after the core Redis story is clear.
- Mention optional components, like Ollama and Google Calendar, as extensions rather than the main point.

## Style

- Sound practical and demo-driven.
- Emphasize what attendees will learn to build.
- Use plain language for program committees and conference audiences.
- Avoid hype, vague AI claims, and unsupported latency or scale claims.

## Source of Truth

If you need project facts, use [references/project-context.md](references/project-context.md) first, then consult the repo README or code for confirmation.
